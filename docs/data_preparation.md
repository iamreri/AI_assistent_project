# Подготовка данных для базы знаний ИИ-ассистента МГТУ им. Г.И. Носова

## 1. Источники

Приоритет источников: **1** — официальный сайт и нормативные документы (основная база),
**2** — служебные системы и законодательство (дополняющая),
**3** — новости и соцсети (опционально, чанки помечаются датой).

| ID | Источник | Что берём | Приоритет | Статус |
|---|---|---|---|---|
| src_001 | magtu.ru/sveden/document.html | Устав, правила приёма, приказы о стоимости, ЛНА | 1 | собран |
| src_002 | magtu.ru/abit | Сроки приёма, испытания, индивидуальные достижения | 1 | собран |
| src_003 | magtu.ru/sveden | Сведения об организации | 1 | собран |
| src_004 | magtu.ru — институты и кафедры | Направления, контакты | 1 | собран |
| src_006 | newlms.magtu.ru | Общедоступные страницы портала | 2 | собран |
| src_007 | timetable.magtu.ru | Расписание — **динамические данные, в базу не зашиваются** | 2 | исключено |

Полный перечень со статусами сбора — `data/sources.csv`.
Что сознательно не собираем: неофициальные сообщества и форумы (противоречия),
персональные данные сотрудников и студентов (152-ФЗ).

## 2. Способ получения данных

- Веб-страницы: скачивание HTML и извлечение текста (инструмент: `requests` + `BeautifulSoup`).
- PDF/DOCX: скачивание файлов из раздела «Документы» и парсинг через `PyMuPDF` и `python-docx`.
- Динамические страницы: сохранение с фиксацией даты среза (`last_checked` в `sources.csv`).
- Соответствие «файл ↔ источник» фиксируется в `data/documents/docs_index.csv`.

**Воспроизводимость:** все шаги автоматизированы в `scripts/prepare_data.py`,
инструкция запуска — `data/README.md`.

## 3. Очистка

Применённые правила (реализованы в `clean_text()`):

1. Удаление номеров страниц и колонтитулов («стр. X из Y»).
2. Склейка слов, разорванных переносом (`прави-\nла` → `правила`).
3. Выпрямление кавычек (`"…"`, `“…”` → `«…»`) и тире.
4. Удаление мягких переносов, лигатур, лишних пробелов и пустых строк.
5. Таблицы из DOCX сериализуются строками `ячейка | ячейка` с пометкой `[ТАБЛИЦА]`.
6. Структура сохраняется: заголовки и нумерация пунктов (5.2.1 и т.п.) не выравниваются,
   они используются на этапе чанкинга как границы и остаются в тексте чанков.

Дедупликация документов: SHA-256 по нормализованному тексту; отчёт —
`data/documents/duplicates_report.csv`.

## 4. Chunking

Подготовлены **два варианта**:

- **Вариант А — фиксированный размер.** Окно ~1600 символов (~500 токенов),
  перекрытие 200 символов, границы выравниваются по абзацам.
- **Вариант Б — по смысловым блокам.** Границы — заголовки (маркдаун,
  «Раздел/Глава/Приложение», нумерация `5.2.1`), абзацы; мелкие блоки
  склеиваются до ~400 символов, блоки крупнее окна режутся с сохранением
  заголовка-шапки в каждом куске.

Файлы: `data/chunks/chunks_fixed.jsonl` и `data/chunks/chunks_semantic.jsonl`.

**Сравнение.** Метрика recall@5 на 10 тестовых вопросах
(`scripts/questions.csv`): поиск TF-IDF, вопрос считается решённым, если в
топ-5 попал чанк с ожидаемым ключевым словом.


**Итог и обоснование:** Выбран вариант Б (семантический чанкинг). Он показал 100% полноту поиска на тестовой выборке, в то время как фиксированный чанкинг пропустил 1 вопрос («Какие вступительные испытания на направление 09.03.01?») из-за разрыва смыслового блока при нарезке. Для дальнейшей работы используется файл `data/chunks/chunks_semantic.jsonl`.

## 5. Metadata

Поля чанка (JSONL): `document_id`, `document_title`, `source`, `date`,
`document_type`, `department`, `page`, `chunk_id`, `text` — согласно заданию.
Добавлены от себя: `variant` (способ нарезки), `section` (ближайший заголовок —
улучшает поиск и позволяет ассистенту ссылаться на пункт документа).

## 6. Проблемы при подготовке данных и принятые решения

| Проблема | Решение |
|---|---|
| Сканированные PDF без текстового слоя | Выявлены в файлах `10-30-552.pdf` и `10-30-566.pdf`. Текст не извлечён (пустые чанки). Для продакшена требуется этап OCR (Tesseract/EasyOCR), для текущего эксперимента файлы оставлены в базе с пустым текстом. |
| Отсутствие необходимых библиотек Python | Ошибка `ModuleNotFoundError` для `fitz`, `docx`, `sklearn`. Решено установкой зависимостей через `pip install pymupdf python-docx lxml scikit-learn`. |
| Несовпадение путей и дисков при запуске | Ошибка поиска файлов из-за работы в разных директориях (C:\ vs D:\). Решено использованием команды `cd /d` для корректного перехода между дисками и проверкой структуры папок. |
| Один документ лежит в нескольких разделах | Дедупликация по хешу текста (SHA-256) реализована в скрипте подготовки. |
| Устаревшие версии правил приёма | Хранится только действующая редакция; старые — помечены архивом. |
| Динамические данные (расписание, цены) | Не зашиваются в базу; план — API-подтягивание. |
| Мусор из PDF (колонтитулы, разорванные слова) | Правила очистки из раздела 3. |

## 7. Правила обновления базы знаний

1. **Периодичность.** Раз в 2 недели проверяем `last_checked` по
   `sources.csv`: если дата изменения страницы новее — документ переоценивается.
2. **Устаревание.** Новый приказ/новая редакция правил → старый документ
   переводится в архив (папка `documents/archive/`), из базы чанков удаляются
   все его чанки (`document_id` фильтром).
3. **Пересборка.** При изменении документа он проходит полный цикл заново
   (извлечение → очистка → чанкинг): чанки не редактируются по кусочкам.
4. **Ответственный.** Ярославна (разработчик пайплайна).
5. **Контроль качества.** Перед заменой документ прогоняется через тестовые
   вопросы `scripts/questions.csv`; recall не должен просесть ниже 95%.

## 8. Итоговый результат

Воспроизводимая база знаний: сырые файлы + реестр + два набора чанков +
скрипты + отчёт. Инструкция воспроизведения — `data/README.md`.

**Статус проекта:** Готов к интеграции в RAG-систему. Основной вектор развития — внедрение OCR для обработки сканированных документов.
